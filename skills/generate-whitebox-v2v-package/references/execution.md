# 执行：四文件 → 规划 → 生图 → 绑定打包

生图接口由用户所在环境提供，本 Skill 不绑定服务商、网址、密钥名或内置图像工具，不自行购买服务。以下请求结构是执行器内部约定，不是任何厂商 API 的参数声明。

当前用户指定生图为 GPT、视频为 SD2.5，两者分别记录。GPT 的实际模型 ID 与请求参数沿用用户现有接口配置，不根据“GPT”猜版本或自动升级。按用户本次要求进入只交提示词或实际生图模式。图片提示词方法见 [gpt-image-environment.md](gpt-image-environment.md)。

## 1. 读取与规划

每组四文件建立独立 job_id。在两份文本与总览上直接读取已有镜头，不重做切镜、不审核剧本、不强制完整看片。视频用作最终 V2V 参考及所需原帧来源。基础媒体读取可取得帧率、尺寸、时长，但不把它扩展成全片视觉检查。

局部图在写最终生图提示词前，先按总览选帧，从本任务视频抽出清晰原帧，读取其必要空间逻辑。全景纯文生图不抽帧。工具操作仍在同一次规划中完成，视频提示词可同时编写，不增加规划模型节点。

规划 agent 可自行保存内部 `关键帧清单.json`，只含一个 `anchors` 数组，各锚点使用 [output-schema.md](output-schema.md) 的既有8字段。这不是第五份用户素材，也不是最终规划JSON，不需要填写占位生图提示词。例如下列仅演示格式，时间和镜号必须换为本任务实际选择：

```json
{"anchors":[{"id":"frame_s01","shot_id":1,"time_s":1.2,"time_precision":"approximate","role":"primary","description":"从本任务总览选定的局部结构画面","frame_number":null,"frame_number_base":null}]}
```

先取帧，尚无需生图 prompt：

```bash
python3 scripts/prepare_image_inputs.py \
  --anchors /project/job_a/关键帧清单.json \
  --video /project/job_a/白模视频.mp4 \
  --out /project/job_a/关键帧
```

读取返回的帧文件后，完成两类提示词。帧仅提供逻辑，不能对白模直接贴图；不需要重新分析整段视频。

保存 `SP输出_v3.json`，同时提取 `视频渲染提示词.txt` 和逐图提示词。规划文本不会因为尚未生图而推迟视频提示词编写。

## 2. 准备实际生图输入

- `text_to_image`：只发送本图 prompt，input_files为空；不传白模帧、总览、原视频、已生成图，也不利用聊天历史图片隐式附图。
- `image_to_image`：按 anchors 顺序复用规划阶段已提取的白模帧，主帧在前、上下文在后；随后按 appearance_sources 顺序附外观图。只有依赖图的非人物资产可不带白模帧。
- 取帧对应本任务视频，按文本的成片标记处理；锚点、ID、路径文字都不能代替真实图像输入。总览是给规划模型读的，不直接传成多格生图输入。
- 若API要求上传，上传选定原帧与依赖图，保留相同顺序及对应关系。若不能接收必需图片，不静默删图改文生图。

可用配套脚本准备请求，通过 `--frame-manifest` 传入前置取帧结果。命令中的路径按实际环境填写；ffmpeg/ffprobe 可在PATH，也可通过参数指定，不依赖原作者路径：

```bash
python3 scripts/prepare_image_inputs.py \
  --plan /project/job_a/SP输出_v3.json \
  --video /project/job_a/白模视频.mp4 \
  --frame-manifest /project/job_a/关键帧/frame_manifest.json \
  --out /project/job_a/生图输入
```

默认拒绝覆盖旧输出。后续依赖准备使用新输出目录，并提供已经生成的图片路径表：

```json
{"img_01": "/project/job_a/图1_场景全景.png"}
```

```bash
python3 scripts/prepare_image_inputs.py \
  --plan /project/job_a/SP输出_v3.json \
  --video /project/job_a/白模视频.mp4 \
  --frame-manifest /project/job_a/关键帧/frame_manifest.json \
  --out /project/job_a/生图输入_下一批 \
  --generated-manifest /project/job_a/已生成图片.json
```

脚本在 `--anchors` 模式只取帧，输出 `frame_manifest.json`；在 `--plan` 配合 `--frame-manifest` 模式校验来源与定位并复用帧，再组装输入。清单缺失、来源或定位不匹配时据实报错，不悄悄重新抽帧。它不解释视频、不做切镜、视觉验图或API调用，只校验执行所需字段，不替代完整规划格式和提示词引用检查。最终输出 `input_manifest.json` 供执行器读取，每图含模式、prompt、input_files及ready/waiting_dependency/error。所有清单都由 agent 根据四文件自动产生。

仅文生图没有 `frame_manifest.json`，最终调用省略该参数。旧版仅 `--plan` 的直接取帧能力保留为兼容入口，本 Skill 默认流程使用前置取帧与结果复用，不借兼容入口把抽帧推迟到写词之后。

脚本需要Python3.8+；抽帧需要FFmpeg5+及ffprobe。仅文生图时不需要视频参数，也不启动ffmpeg。退出码0表示已准备或等待依赖，1表示存在逐图错误但其余结果仍保留，2表示全局输入或输出目录错误。只有ready项可交给生图API。

帧号已知时按编号基数换算解码帧索引；时间定位按媒体显示时间戳，归一化首画面为0。记录实际取帧时刻，不能把“约在镜头中间”称为精确命中总览格。不要取最后一镜的结束时刻当作可解码帧。

## 3. 生成与批量

内部单图请求至少包含 job_id、image_id、generation_mode、prompt、input_files。将这些内容映射到用户实际生图服务的参数，不把 v3 字段原样冒充厂商参数。选择工具时要支持纯文字零图片输入和所需的参考图片输入。

每图默认一次有效生图请求，不调用视觉质检模型，不计算质量分，不自动修改提示词或重生成。图像API本身的返回不等于已做视觉验收。

无依赖图片和不同视频可按接口并发限制并行。有依赖的图片等上游成功返回且文件可读取即可继续，**不等待视觉合格**。优先减少不必要的依赖，避免把其他区域背景、未声明设施及阶段状态带入下游；已明确声明的本区域环境设计可按继承范围使用。

维护请求ID和已有结果，断点继续时只执行未成功的任务；脚本再次生成ready输入不意味着应再次调用API。网络失败按接入服务的有界策略处理，结果不明先查询原请求／使用幂等能力，防止重复计费；不把网络重试变为质量改图。

每个任务独立保存结果及失败原因，某张接口失败只暂停其依赖，其他任务继续。批量键为 job_id + image_id；不按文件列表位置或返回顺序猜图号。

## 4. 生成后直接绑定

图片返回后保存到项目目录，绑定 id、ref、真实文件路径。可以机械检查文件存在、可读取或解码、编号唯一、依赖齐全，不能做内容比对、人工挑片、背景正确性评分或修图循环。

缺图不删除对应引用、不重排后续图号，不把失败图换个用途伪装成完成。保存已产出部分和缺项记录；完整素材齐全时才标记 package_ready。此状态仅表示可提交的文件齐全，不表示美术或视频效果已验证。

用户后续明确要求修改某张图时，将其作为新请求处理；这不是本流程自动步骤。同步更新该图的提示词和绑定，受影响的外观依赖据新的任务范围处理，不默认无限重试。

## 5. 提交包

每个任务的可移植目录示例：

```text
项目_提交包/
  视频1_白模.mp4
  图1_场景全景.png
  图2_关键区域.png
  视频渲染提示词.txt
  提交清单.json
  创作资料/
    SP输出_v3.json
    生图提示词.txt
    分镜总览.jpg
    剧本与分镜导演卡.txt
    视频续作提示词.txt
    生图输入/                  按需存在
    生成记录.json
```

示例图数不是固定数量。提交清单记录 @视频1 与 @图N 的实际文件对应、目标模型、媒体基本信息、缺项及 package_ready；执行记录另存接口结果与输入顺序。不要生成“视觉检查通过”文档。

原白模总览和依据帧留在创作资料，不自动作为最终 @图N 上传。最终 V2V 素材是白模视频、生成的参考图和视频提示词。

可打成每任务ZIP和批次总ZIP。用户只要求交付包时到此结束；用户明确要求提交平台时再按已有授权执行，不因Skill本身越过交付范围。缺少API能力时完整交付规划与取帧资料，并准确说明实图尚未生成。
